## Objective

v0.1.9 adds the smallest useful shared household Task capability while preserving the existing Calendar and Reminder domains.

- An Event represents when something happens.
- A Task represents something that remains to be completed.
- Every Task belongs to exactly one Space.
- Current Space members collaborate on the same Task set through Supabase persistence, RLS, and Realtime.

Success means two authenticated members can create, view, assign, edit, complete, reopen, and delete Tasks with cross-device Realtime synchronization. Slice 1 Task backend foundation and the status-ownership corrective patch were applied to Production with verified postflight. Slice 2 UI/Realtime client passed user-run authenticated A/B and 320px acceptance locally. The frontend was then deployed through Vercel; Slice 3 user-run Desktop A/B Production acceptance and iPhone mobile smoke passed. Details are in [Testing](./TESTING.md).

## Frozen Product Semantics

### Creator and ownership

- `created_by` records creator attribution only.
- The creator receives no exclusive permission; status transitions follow the current assignment rule below.
- `created_by` is immutable after creation.

### Assignment

- `assigned_to_user_id = <current member id>` means that member is responsible.
- `assigned_to_user_id = null` means shared responsibility.
- Assignment does not restrict visibility, title/due-date editing, reassignment, or deletion; it owns status transitions when non-null.
- A non-null assignee must be a current member of the same Space as the Task.
- Any current Space member may assign, reassign, or change a Task to shared.
- If an assigned member leaves the Space, the Task automatically becomes shared by setting `assigned_to_user_id` to null.
- Slice 1 verified PostgreSQL 17.6 in the local Supabase target and uses a composite foreign key from `(space_id, assigned_to_user_id)` to `space_members(space_id, user_id)` with column-specific `ON DELETE SET NULL (assigned_to_user_id)`. Removing an assigned membership therefore preserves the Task and `space_id` while clearing only the assignee; no cleanup trigger is needed.

### Completion

- Status is exactly `open` or `completed`.
- New Tasks default to `open`.
- Any current Space member may complete or reopen a Shared Task. Only the current assignee may complete or reopen an Assigned Task.
- A member taking over another member's Task must first reassign it in one UPDATE, then change status in a second UPDATE. The database evaluates a status transition against the UPDATE's `OLD.assigned_to_user_id`; reassignment and status change in one UPDATE cannot bypass ownership.
- v0.1.9 does not store `completed_at`, `completed_by`, or completion history.

### Due date

- `due_on` is optional.
- It is a PostgreSQL `date`, with no time or timezone.
- It does not create, update, or duplicate a Calendar Event.

### Scope

- A Task has an explicit `space_id`.
- A Task does not have Event-style `scope` or `owner_user_id` fields.
- Space membership controls visibility; assignment expresses responsibility.

## Frozen Data Contract

v0.1.9 adds exactly one product table: `public.tasks`.

| Field | Contract |
| --- | --- |
| `id` | Generated UUID primary key |
| `space_id` | Required reference to the existing Space; immutable after creation |
| `created_by` | Required authenticated creator attribution; immutable after creation |
| `assigned_to_user_id` | Nullable; null means shared; non-null must be a current member of the same Space |
| `title` | Required canonical value; trimmed length 1–200 characters and no leading/trailing whitespace |
| `status` | Required `open` or `completed`; defaults to `open` |
| `due_on` | Nullable PostgreSQL `date` |
| `created_at` | Required timestamp using the existing project convention |
| `updated_at` | Required timestamp using the existing touch pattern |

Database invariants are authoritative. The frontend may trim and validate for usability, but it is not the final security boundary. Slice 1 chooses the simplest deterministic title enforcement that satisfies the stored-value contract without adding a validation framework.

The table must also receive:

- one reasonable list-oriented index;
- minimal immutable-identity enforcement for `space_id` and `created_by`;
- same-Space current-member assignment validation;
- conventional authenticated CRUD grants and RLS policies;
- inclusion in the existing Supabase Realtime publication;
- the existing compatible replica-identity pattern needed for Space-filtered delete delivery.

Slice 1 uses one list index on `(space_id, status, due_on, created_at, id)`. PostgreSQL ascending order already places null `due_on` values last, and the remaining keys match the frozen stable list order. Member-leave behavior uses the verified FK-native mechanism described above.

## Permission Model

| Operation | Frozen permission |
| --- | --- |
| Create | Any current member of the target Space; `created_by` must equal the authenticated user |
| View | Every current member of the Task's Space |
| Edit title or due date | Every current member of the Task's Space |
| Change assignment | Every current member; target must be a current same-Space member or null |
| Complete or reopen | Shared: every current member; Assigned: only the current assignee, judged from the row before the UPDATE |
| Delete | Every current member; UI requires confirmation |
| Former or non-member access | None |
| Creator-specific privilege | None |
| Assignee-exclusive privilege | Complete/reopen on assigned Tasks only; no exclusive visibility, edit, reassignment, or delete right |

RLS, database constraints, membership validation, immutable identity, and the status-ownership trigger are the authorization and integrity boundary. Frontend visibility or disabled controls are UX only. The original all-member complete/reopen rule was corrected after real A/B Slice 2 acceptance revealed that A could complete B's assigned Task.

Ordinary Task CRUD should use direct Supabase/PostgREST operations. Do not add a Task CRUD RPC unless Slice 1 demonstrates a concrete atomicity requirement that cannot be met safely by the conventional table path.

## Security and Abuse Cases

Slice 1 must prove the following at the database boundary:

- a non-member cannot read or mutate Tasks;
- a member cannot create a Task in a Space they do not belong to;
- a client cannot forge `created_by` for another user;
- a client cannot move an existing Task to another Space or change its creator;
- an assignee cannot be selected from another Space or from former members;
- title values that are blank, edge-padded, or longer than 200 characters are rejected as canonical stored values;
- invalid status values are rejected;
- Realtime visibility does not broaden beyond RLS-authorized Space data.

Task titles remain plain text rendered through React's normal escaping. v0.1.9 adds no HTML rendering, external URL fetch, file input, secret, or new authentication flow.

## Realtime Model

- Reuse Supabase Realtime; do not introduce another synchronization architecture.
- Subscribe to Task INSERT, UPDATE, and DELETE changes filtered by the explicit current/selected `space.id`.
- Reload the canonical Task list for that Space after a change, matching the existing Event pattern.
- A create on device A appears on device B without refresh.
- Assignment, title, due-date, completion, and reopen changes synchronize.
- Deletion synchronizes through the existing compatible filtered-delete replica-identity pattern.

## Calendar Boundary

- `tasks.due_on` is Task metadata only.
- v0.1.9 does not copy a Task into `events`, create an Event, update an Event, participate in Event recurrence, or introduce dual persistence.
- A future version may design a read-only Calendar projection of due Tasks without duplicating persistence. That work is not part of v0.1.9.

## Reminder Boundary

v0.1.9 does not change or reuse:

- `events.reminder_kind`;
- `send-reminders`;
- `reminder_deliveries`;
- Supabase Cron or `pg_net` scheduling;
- Web Push delivery or recipient resolution;
- ordinary or recurring Event Reminder projection.

Task Reminder is deferred. The `CLOSED / PASS` v0.1.8 Reminder architecture stays closed.

## Multi-space Decision

Decision: `MULTISPACE_NOT_REQUIRED_FOR_V019`.

Evidence:

- Task identity explicitly includes `space_id` from the first version.
- Existing membership and RLS helpers accept explicit Space IDs.
- Realtime can filter by an explicit current/selected Space ID.
- Current one-Space assumptions are concentrated in the unique membership index, create/join lifecycle, and frontend current-Space selection.
- A later Multi-space version can change membership lifecycle and add a Space selector without changing Task identity or assignment semantics.

Future-compatibility requirements:

- Task implementation receives and uses the explicit current/selected `space.id`.
- It never derives a Space implicitly from user identity.
- It does not add another one-space-per-user constraint.
- It never omits `space_id` from Task persistence or Realtime filtering.

v0.1.9 does not implement Multi-space, a Space switcher, multi-space onboarding, or broad membership/RLS rewrites.

## Complexity Budget

The approved budget is:

- one new product table: `tasks`;
- one reasonable list-oriented index;
- bounded constraints and assignment validation;
- minimal immutable-identity enforcement;
- conventional RLS CRUD policies and grants;
- direct Supabase CRUD;
- the existing Realtime pattern;
- no new dependency unless implementation proves it necessary and receives approval.

Do not add an Edge Function, Cron job, queue, workflow engine, local persistence, external storage, generic activity log, or another synchronization layer.

## Minimal UI Scope

### Entry and screen structure

- The existing Calendar remains the initial screen. Its header already shows the current `space.name` above the month, next to existing Calendar controls. Make that name a clearly tappable current-Space entry; it opens the Space Hub. This is the only new Calendar entry/control. Keep the month, Today/Week/Month switch, date controls, Event `+`, Event interactions, member shortcut, notification/logout controls, and existing invite panel behavior intact.
- Use bounded in-app screen state `Calendar → Space Hub → Tasks → Completed Tasks`, with back controls `Completed Tasks → Tasks → Space Hub → Calendar`. Returning to Calendar preserves its selected date and view mode. Do not add routes, an App Shell rewrite, a top-level `Calendar / Tasks` switch, or the future four-destination navigation.
- The Space Hub is for the one existing current Space, not a Space selector. Show the actual `space.name` as its heading; a `成员 · N` action opens the existing Member Sheet; an `邀请码` block reuses the existing copy/rotate capability; and one `Tasks` row shows the live `N 项待完成` count and a chevron. Do not show future module entries or disabled placeholders.

```text
← 日历               我们俩
成员 · 2                         >
邀请码 [现有复制 / 轮换能力]
Tasks       4 项待完成           >
```

### Tasks and Completed Tasks pages

- Tasks page header: back to Space Hub, `Tasks`, and a page-local `+` for new Task. Show `待完成 · N`, then every open Task as a single-column row. An eligible member can use the left circle to complete; another member's assigned Task shows a noninteractive circle. The separate title/details area always opens its edit Sheet. The secondary line shows assignment and optional localized date only, e.g. `Ping · 9月25日`, `共同 · 9月28日`, or `对方`. Do not imply a due time, reminder, priority, or status audit.
- After the open list, show a single `已完成 · N >` row, including when N is zero. It opens a separate Completed Tasks page; completed rows are not expanded on the main Tasks page. Empty open state: `暂无待完成事项` with the page-local `+` still available.
- Completed Tasks page header: back to Tasks and `已完成`. Show all completed Tasks, no pagination UI or framework; the data load must not silently truncate the list at a server row limit. Each row has a visible completed mark, title, assignment/optional date, and `重新打开` only for an eligible member. Tapping its title/details always opens the same edit Sheet, including Delete. Empty state: `暂无已完成事项`.
- Open ordering is `due_on` ascending, null due dates last, then `created_at` ascending, then `id` ascending. Completed ordering uses the same stable fields because Slice 1 stores no completion timestamp; do not claim completion-recency ordering. Counts reflect canonical current-Space rows.

```text

待完成 · 4
○ 买洗衣液
  Ping · 9月25日
○ 订酒店
  共同 · 9月28日
○ 取快递
  对方
已完成 · 12                    >

← Tasks           已完成
✓ 已缴水费          重新打开
  共同 · 9月20日
```

### Create and edit Sheet

- The page-local `+` opens a simple bottom Sheet using the existing Event/Member Sheet visual language: mobile bottom attachment, scrollable content, safe-area padding, close control, and explicit save. The create Sheet contains only `标题`, `分配给`, and optional `截止日期` (native date input with a clear/no-date choice). New Tasks begin `open`; the default assignment is `共同`, with no due date.
- Assignment choices are `共同` plus the actual current Space members. Use each member's existing `profiles.display_name` when non-empty. In v0.1.9's current two-member stage only, when a display name is empty, the UI may label the authenticated member `我` and the other actual member `对方`. These are contextual UI fallbacks, not durable member roles or identity values; persist member IDs, never display strings. Do not encode `对方` / `partner` as a long-term member identity model. Future Multi-space / multi-member experiences will use generic member display logic. Never derive a public label from email/Auth metadata or add a nickname/schema. For a one-member Space, show only `共同` and that member, using `我` only for the authenticated member if needed.
- A Task title/details tap opens the edit Sheet with the same three editable fields populated from the canonical Task. The edit Sheet also contains Delete. A completed Task stays completed when its details change; `重新打开` is a separate action. Trim title input; reject blank or >200 characters before save, and surface database errors without closing the Sheet.
- Delete opens an explicit second confirmation that names the Task and offers cancel/delete; only confirmation sends DELETE. No swipe-to-delete. Discarding/closing a Sheet does not save.

### Interaction and mobile behavior

- Eligible Open Task circle: `○ → ✓` on tap, update `open → completed`, remove it from the Open list and increment the Completed count. Eligible Completed `重新打开` sets `completed → open`, removes it from Completed and restores it in the sorted Open list. For another member's assigned Task, neither action is clickable; its edit Sheet still allows title, due date, and reassignment. Prevent duplicate writes while an operation is pending; on failure show an error and keep/restore canonical state.
- Use the existing `max-w-3xl` centered shell and project colors/typography. At 320px width, each page is a single column; titles wrap, count/chevrons remain readable, row actions have separate touch targets, and no horizontal scrolling occurs. Sheet content scrolls above the mobile keyboard and respects the bottom safe area. Buttons are keyboard reachable and icon-only controls have accessible names.
- Reuse the existing `space_id`-filtered `postgres_changes` pattern for INSERT/UPDATE/DELETE and reload the canonical Task list after changes. Keep the subscription active for the current Space so Hub counts and both lists update without manual refresh. A local successful mutation also reloads its canonical result; loading, empty, and error states are explicit. RLS remains authoritative.

## Risks

- Collaborative permissions intentionally allow any current member to edit or delete any Task; this is household collaboration, not enterprise RBAC.
- Status-only completion has no actor/time audit trail. That is an explicit MVP tradeoff.
- Date-only due values cannot express a time-of-day deadline. Adding time would change the product boundary and is deferred.
- No member-removal UI currently exists, so member-leave behavior must still be tested directly at the database boundary in Slice 1.
- Local and Production targets both run PostgreSQL 17.6 and support the selected column-specific composite-FK delete action; Production compatibility preflight passed before the backend patch was applied.
- The current frontend has a single-Space shell and a large `App.tsx`; Slice 2 may extract a focused Task component and a bounded current-Space entry, but it must not turn that need into a full navigation, shell, or routing rewrite.

## Boundaries

### Always

- Use explicit `space_id`, database-enforced membership, RLS, and deterministic validation.
- Keep migrations additive and update both the incremental patch and fresh-install schema.
- Use temporary or injected test data/paths and preserve Supabase as canonical persistence.
- Run the smallest relevant checks plus full regressions proportionate to each slice.

### Ask first

- Begin any implementation slice.
- Add a dependency, RPC, Edge Function, deployment, Production mutation, or scope item not frozen here.
- Change authentication, Space lifecycle, member capacity, Multi-space behavior, Event semantics, or Reminder architecture.

### Never in v0.1.9

- Treat assignment as authorization.
- Rely on frontend validation or hidden controls as the permission boundary.
- Infer a Task's Space from the user instead of persisting explicit `space_id`.
- Create Task/Event dual persistence or silently enable Task reminders.
- Store Task business data in repository-local or filesystem persistence.
