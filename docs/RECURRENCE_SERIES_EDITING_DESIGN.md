# v0.1.7.3 Design: Recurrence Editing Semantics

## Status

**Design only.** This document does not authorize a database migration, RPC, UI, RLS, Realtime, or production change.

v0.1.7.2 projects `events` plus `event_occurrence_exceptions` into `CalendarOccurrence[]`. A rendered recurring occurrence now has a stable identity of `${source_event_id}:${occurrence_date}`, where `occurrence_date` is the scheduled `YYYY-MM-DD` in the source rule timezone. v0.1.7.3 defines the mutation semantics that must use that identity.

## Current behavior and gap

The current click path is:

```text
EventCard(occurrence)
  -> DaySection onEdit(occurrence.source_event)
  -> CalendarApp setEditingEvent(source event)
  -> EventSheet
  -> events.update(...).eq('id', event.id) / events.delete().eq('id', event.id)
```

`CalendarOccurrence.source_event` is the original `events` row. `EventSheet` therefore receives no occurrence key or scheduled instant. For a recurring source its direct update/delete changes every projected occurrence of that source segment. It cannot currently express only-this or this-and-following.

## Terms and invariants

| Term | Meaning |
| --- | --- |
| Segment | One recurring `events` row and its baseline rule, exceptions, and optional cutoff. |
| Logical series | The root segment and all split descendants with the same `series_id`. |
| Occurrence key | `occurrence_date`: scheduled local date in the source recurrence-rule timezone. Never derive it from viewer timezone, UTC date, or an overridden display time. |
| Scheduled instant | The source rule timezone instant generated for an occurrence key before applying an override. |

- `recurrence_until` is an exclusive scheduled-start instant: the segment emits only candidates earlier than it.
- `series_id` identifies the root of a split lineage. A root has `series_id = id`; every child copies the root ID.
- `parent_event_id` points to the immediately preceding segment; it is lineage, not an exception owner.
- An exception is permanently segment-local through `event_occurrence_exceptions.event_id`. It is never moved to a child segment.
- Existing schema names are authoritative: `event_id`, `occurrence_date`, `exception_type`, and `override_data`. Do not use field names from the older design draft such as `source_event_id`, `occurrence_key`, or `kind`.

## Product semantics

The scope chooser appears only when the clicked item is a manageable recurring occurrence. It must carry the complete occurrence context: `source_event_id`, `occurrence_id`, `occurrence_date`, source rule timezone, and original scheduled instant. Non-recurring events keep the existing one-row edit/delete path; personal events remain read-only for non-owners.

After a split, the UI must call a segment a **series segment**. For editing, “所有事件” means every occurrence generated by the selected segment, not a rewrite of independently changed descendant segments. For deletion, “删除所有重复事件” means the complete logical-series lineage, as decided below.

### Edit

| Choice | Persistent operation | Result |
| --- | --- | --- |
| 仅此事件 | Upsert `(event_id, occurrence_date)` with `exception_type = 'override'`. | Only the selected occurrence changes. |
| 此后所有事件 | Atomically close old segment and create a child segment. | Selected and later scheduled occurrences use the child baseline. |
| 所有事件 | Update the selected source segment baseline. | Its non-exception occurrences update; overrides/deletions still win. |

### Delete

| Choice | Persistent operation | Result |
| --- | --- | --- |
| 仅此事件 | Upsert `(event_id, occurrence_date)` with `exception_type = 'deleted'` and `override_data = null`. | Only the selected occurrence is omitted. |
| 此后所有事件 | Atomically set the selected segment cutoff and remove now-unreachable exceptions after confirmation. | Selected and later occurrences in that segment disappear. |
| 删除所有重复事件 | Remove the complete logical-series lineage. | Root, child segments, and all lineage exceptions are deleted atomically. |

## A. Only this event

### Edit one occurrence

Use `event_occurrence_exceptions`, not an `events` update. The upsert key is the clicked occurrence's `(source_event_id, occurrence_date)`.

`override_data` may contain only the v0.1.7.2 projection-safe fields: `starts_at`, `ends_at`, `title`, and `description`. If only `starts_at` changes, projection retains the source duration. The source `id`, space, owner, scope, recurrence rule, lineage fields, and occurrence identity remain immutable.

Changing `all_day` for only one occurrence is not currently supported: the v0.1.7.2 override contract intentionally does not project an `all_day` override. The scope UI must disable that control for only-this editing rather than silently discarding it. Expanding that contract needs a later, explicitly approved reader/type/test change.

### Delete one occurrence

Upsert a `deleted` exception. If an override already exists for the same key, the replacement deletion wins. Repeating delete is idempotent. “Restore occurrence” is a later UI action that deletes the exception row; it is not required for the first v0.1.7.3 slice.

## B. All events in the selected segment

Update the selected `events` row's editable baseline fields: title, description, starts/ends, all-day state, and recurrence rule. This is the existing direct-update behavior, but it must be reached through an explicit scope choice for recurring occurrences.

The update affects all generated occurrences in that source segment, including future ones. Stored exceptions remain segment-local and take precedence during projection. Before a recurrence-rule or timezone change is accepted, the mutation boundary must calculate exceptions that no longer describe generated scheduled keys and return their count. The user must cancel, explicitly remove those exceptions, or preserve an equivalent schedule; never silently orphan or discard them.

This scope is intentionally not a bulk rewrite of every row sharing `series_id`: a previous split represents a deliberate change in baseline and must preserve historical and child-segment behavior.

## C. This and following: atomic series split

Example: Event A is weekly Monday 20:00. The user changes the 2026-08-03 occurrence and following occurrences to 21:00.

```text
Before
  A (id=A, series_id=A, parent_event_id=null, recurrence_until=null)
  weekly Monday 20:00

After
  A (id=A, series_id=A, parent_event_id=null,
     recurrence_until=scheduled instant for 2026-08-03 20:00)
  B (id=B, series_id=A, parent_event_id=A, recurrence_until=null)
  weekly Monday 21:00, starts_at=2026-08-03 21:00
```

The selected occurrence belongs to B, not to an override on A. A emits only through 2026-07-27; B starts its recurrence anchor at the selected occurrence's edited baseline. The child copies immutable identity fields (`space_id`, `scope`, `owner_user_id`, and `created_by`) and receives a new row ID.

The client must submit the original source occurrence key and scheduled instant, the edited child baseline/rule, and an optimistic concurrency value (for example, source `updated_at`). The server-side mutation must lock the source row and relevant exceptions, verify permission and candidate validity, then perform cutoff, child insert, and exception cleanup in one transaction. A client-side sequence of update/insert/delete is not safe.

### Exception handling at a split

Exceptions never migrate or copy:

- Keys before the split remain on A and continue to apply.
- The selected key and future keys attached to A become unreachable after A's cutoff.
- The RPC returns their count before confirmation, then deletes precisely those unreachable A exceptions in the same transaction as the split.
- B begins with no exceptions. If the user wants a later exception such as an existing 2026-08-10 override, they recreate it for B after the split.

This avoids assigning an old override to a changed baseline without explicit user intent. It also prevents duplicate exceptions on A and B for the same logical future date.

### Delete this and following

No child is created. In one transaction, validate the selected scheduled occurrence, set the source `recurrence_until` to its scheduled instant, count-confirm and delete exceptions on that source with keys at or after the cutoff, and return the updated source. Earlier history stays intact.

## Delete-all lineage rule

The current foreign keys use `ON DELETE RESTRICT` for both `series_id` and `parent_event_id`. A direct `events.delete()` can therefore fail when the selected segment is referenced by a child (and deleting a root is incompatible with children that retain its `series_id`). The v0.1.7.3 implementation must not present a destructive option that can fail after the user confirms.

Approved rule: “删除所有重复事件” invokes one RPC that identifies the root and every descendant in its logical lineage, checks permission for every affected row, deletes child segments newest-to-oldest, then deletes the root. Their exceptions are deleted with the lineage. This is not an implicit side effect of a selected-segment `events.delete()`.

Deleting only a historical segment while retaining descendants remains out of scope because it requires an explicit lineage re-rooting algorithm and migration/repair rules.

## Database and permission design for a later implementation

The v0.1.7.1 schema provides the foundation; no new table is required for the minimum v0.1.7.3 feature. A later additive patch should add:

1. Validation that lineage fields preserve the same immutable event identity and that parent/root links are coherent.
2. Guardrails for `recurrence_until` against the source rule and segment start.
3. Permission-checked, fixed-`search_path` transactional RPCs for only-this upsert, split, end-from-here deletion, selected-segment update with exception impact analysis, and logical-series deletion.
4. A server-authoritative candidate check using the recurrence contract; the client remains a convenience validator only.
5. Optimistic concurrency checks (`updated_at` or an explicit revision) so two editors cannot silently overwrite a split or exception change.

Existing exception RLS already grants members read access and source-event managers mutation access. Keep that ownership model; do not broaden `events` RLS. RPCs must independently recheck `auth.uid()` and `can_manage_event` for every affected source row, never trust a client-supplied `space_id`, `series_id`, or owner.

## Realtime and client integration

The implementation must subscribe to `event_occurrence_exceptions` as well as `events`, then reload or merge both and re-run projection. For a split transaction, clients may receive child insert, old-row update, and exception deletes in any observable order. The UI must tolerate intermediate payload order by reloading the source event/exception set before declaring the operation complete.

The choice sheet needs: occurrence display values, source baseline values, selected occurrence key, original scheduled instant, source timezone, available scopes, count-confirmation text for affected exceptions, and conflict/error states. It must make clear when an action targets one occurrence, one segment, or the entire logical lineage.

## Implementation slices and acceptance criteria

1. **Mutation contracts and SQL tests:** additive patch and pgTAP/RPC tests for permissions, atomicity, cutoff, exception cleanup, and lineage deletion.
2. **Only-this UI slice:** occurrence-aware edit/delete chooser and exception upsert; unit tests for identity, timezone key, duration, and projection.
3. **This-and-following UI slice:** split/end-from-here RPC integration, count confirmation, optimistic conflicts, and old/new segment projection tests.
4. **All-events and Realtime slice:** explicit selected-segment semantics, leaf/logical-series delete behavior, two-client reload/reprojection tests.

Before release, test shared and personal-owner cases, non-owner/non-member denials, deleted/override behavior around a split, rollback on induced failure, Today/Week/Month projection, desktop/iPhone/Android scope sheets, and two-user Realtime propagation.

## Out of scope

- Materialized occurrence rows, series merge, this-and-following exception migration, undo history, reminders, external calendar sync, and new timezone dependencies.
- Schema/RLS changes or deployment from this design task.
