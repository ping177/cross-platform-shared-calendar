# v0.1.14 — 回顾（Structured Check-in）设计冻结与实施契约

Status: `V014_REVIEW_DESIGN_FROZEN`（产品契约保持冻结；实施进度以 [Project State](./PROJECT_STATE.md) 为准）。v0.1.13 是已验收的用户可见前端基线；v0.1.14 Slice 1 backend 已在 Production 应用并通过只读 postflight。

本文件是 v0.1.14 的 canonical 产品、数据、权限、UI 与验收契约。长期 Space 归属和模块规则见 [Shared Life Architecture Freeze](./SHARED_LIFE_ARCHITECTURE.md)；已部署的成员退出、移除、转让和删除规则见 [Decisions](./DECISIONS.md)。面向用户统一称「回顾」；`review` 仅作为现有模块键及内部数据库标识。

## A. FINAL_DATA_MODEL

- `review_rounds` 是唯一的 Space-owned 回顾本体：`id`、`space_id`、创建时固定的正整数 `round_no`、实际回顾日期 `review_date date`、`created_by`、`created_at`。`space_id` 引用 `spaces` 并随整个 Space 删除而级联；`unique(space_id, round_no)`。没有周期、封存、完成锁定、单次删除或上一轮外键。
- `review_entries` 是该轮的 participant snapshot：`review_id`、`user_id` 唯一确定一位参与者，外加 `focus`（近期专注事项）、`progress`（近期进展）、`problems`（面临问题）、`next_plan`（下一步计划）、`content_revision`、可空的 `filled_revision` 和内容更新时间。四项文本均可空或为空串，不要求任一具体字段必填。
- 创建 RPC 在同一事务内为当时全部合格成员各建一行空 entry：Personal 恰好一行；Shared 恰好两行。之后不增补、不替换、不因成员变更改写这些行。`review_entries.user_id` **不得**用对 `space_members(space_id,user_id)` 的级联删除外键，否则 leave/remove 会破坏历史。单次回顾不提供 entry 删除权限。
- 采用数据库约束与受控写入保护 `round_no`、`space_id`、`review_id`、`user_id` 和 revision；不要靠客户端只读控件保证身份不可改。为 Space 内日期倒序列表及同轮 participant 读取建立必要索引，不创建通用内容或参与者框架。

## B. FINAL_PARTICIPANT_AND_MEMBERSHIP_RULES

访问条件是**当前仍为该 Space 成员，且自己的 `review_entries` 行存在于该轮**；两条件必须同时满足。满足条件的参与者可读该轮本体与双方 entry，只能改自己的 entry。成员 leave/remove 后保留两份历史 entry，但离开的用户立即失去读取和写入权限；仍在 Space 的原参与者继续看双方历史。后来加入者不属于旧轮 participant，不能读、补写或编辑旧轮；仅参加加入后创建的轮次。同一历史参与者后来重新加入原 Space，恢复当前成员身份后即可重新访问自己参加过的旧轮，无恢复表或迁移。

Shared 新建要求创建事务内存在完整两名当前成员；现有数据库已限制 Shared 最多两人。Shared 暂时只剩一人时旧轮保留并可由仍在 Space 的原参与者查看、修改自己的内容，但不能新建；第二名成员加入后才恢复新建。Personal 由其唯一成员随时新建一人回顾。不建立 Shared 单人回顾或三人以上回顾模式。

## C. FINAL_RLS_AND_RPC_BOUNDARIES

- 两表启用 RLS。`SELECT` 必须同时证明当前 Space membership 和本轮 participant 身份；entry 的读取还要限定为这轮的行。不能复用仅检查 `is_space_member(space_id)` 的 Event/Task 读策略。若父表与 entry 表策略互查导致递归，用窄的 `SECURITY DEFINER` 判定函数完成同一条件，并固定安全 `search_path`、最小 EXECUTE 权限；不可把调用者提供的用户 ID 当授权依据。
- 客户端没有两表直接 `INSERT/UPDATE/DELETE/TRUNCATE` 权限；新表按 v0.1.13 lifecycle ACL 边界核对 `anon`、`authenticated`、`service_role`，仅给 `authenticated` 必需的受 RLS 约束的读取权。窄 RPC：`create_review_round(space_id, review_date)`、`save_my_review_entry(review_id, four_fields)`、`mark_my_review_filled(review_id)`、`correct_review_date(review_id, review_date)`。具体 SQL 参数名可遵守项目 `p_` 习惯；签名的能力边界不变。全部以 `auth.uid()` 确定调用者，并在服务器校验当前成员、该轮 participant（创建时除外）及 `review` 模块 `enabled=true`。新建、保存、标记、日期更正均不能通过直接 API 越权；不给客户端传 `round_no`、participant 或 revision 的写入口。
- 写入时与成员变更及模块关闭正确串行化：沿用 v0.1.13 的 Space 行锁边界，并对 `review` 模块开关的并发作同等保护；锁后重验 membership、participant 和模块状态。`SECURITY DEFINER` RPC 要收紧 `search_path`、撤销默认公共 EXECUTE，仅授权 `authenticated`。不改变既有 Event/Task 授权语义。
- `delete_shared_space()` 删除整个 Space 时，回顾本体与 entries 随 `space_id` 级联清除；leave/remove **不得**清除回顾 entry。实现时更新 Space 删除确认文案，明确包含回顾。

## D. FINAL_NUMBERING_AND_DATE_RULES

创建 RPC 先锁定目标 `spaces` 行，确认模块及 Personal 一人或 Shared 两人条件，再取该 Space `max(round_no)+1`、插入本体和 participant snapshot；唯一约束兜底。同 Space 并发创建会顺序得到不同编号，不承诺把两次创建自动合并。`round_no` 永久不改，不按日期、年度或成员变化重排；它只用于并发唯一性、稳定排序、游标和上一份计划定位，不作为用户可见序号。没有单次删除。`review_date` 是独立的本地日历日期，创建时由 UI 明确提交，允许事后更正。日期更正仅限当前成员且该轮 participant，经窄 RPC 只改日期；不改变编号、participant、前一轮关系。历史列表按 `review_date DESC, round_no DESC`（再加稳定 ID 次序）显示；同日可以有多份回顾。

## E. FINAL_ENTRY_STATUS_RULES

四项内容全空或仅有空白字符时显示「未填写」，且不得标记「我已填写」。否则：`filled_revision IS NULL` 为「编辑中」；`filled_revision = content_revision` 为「已填写」；内容在标记后变化、`content_revision > filled_revision` 为「有更新」。全空判断优先于 revision 判断，包括已填写后把四项清空的情形。服务器仅在持久化内容实际变化时递增 `content_revision`；相同内容重复保存不递增。标记操作仅在非空白时将 `filled_revision` 设为当前 `content_revision`；再次修改后回到「有更新」，再次标记后回到「已填写」。版本字段不能由客户端直接写入。

## F. FINAL_MODULE_ENABLEMENT_RULES

继续使用每 Space 的 `space_modules(space_id, module_key, enabled)`；`review` 键已在 schema 中，缺行视为 disabled。仅 Space owner 能通过现有 `set_space_module_enabled` 的窄扩展开启/关闭「回顾」，其他成员只读状态，客户端不能直接改 `space_modules`。`enabled=true` 时正常显示、创建和编辑；`false` 或缺行时该 Space 不进入回顾模块正常选择器，不能创建、保存、标记或更正日期。关闭不删除历史，重开后历史重新出现。没有模块关闭但在普通 UI 浏览历史的旁路，也没有 archive/read-only module mode。回顾的选择器状态独立于 Calendar、Tasks 和空间管理选择。

## G. FINAL_UI_CONTRACT

- 功能中心仅在实现后增加真实「回顾」入口，不放占位卡。回顾首页使用独立的单 Space 选择器，只列出当前成员且 `review` 已开启的 Space；首版不做跨 Space 混排。首页显示该 Space 在当前 RLS 可见范围内的 authoritative exact count：`共 N 篇回顾`，不能用已加载行数代替。历史行按日期倒序并可继续分页，只显示日期与该轮参与者双方状态；Personal 仅本人状态，不露正文摘要或 `round_no`。右上角 `+` 先显示并确认目标 Space 与实际日期，确认后创建空轮并进入详情。Shared 不满两人时禁用创建并说明原因。没有可选 Space 时显示开启指引，不暴露 disabled 历史入口。
- 详情以日期作为可见身份，不显示 `round_no`。Shared 桌面「我」左、「对方」右；手机用「我／对方」切换且默认「我」；Personal 单列。历史轮对后来成员根本不可见，因此不出现“新成员编辑旧轮”的第三列。对方内容只读；本人内容可修改并可操作「我已填写」。两端的每个文本框固定高度、框内纵向滚动并保留换行；「近期专注事项」较矮，其余三个等高且较高。至少核对 320px 与桌面宽度、键盘访问、长文换行、加载/失败/重试与保存状态。
- 无 Realtime。进入/返回页面、创建、保存、标记、日期更正、主动刷新或重新聚焦时读取当前状态；不以轮询或全局订阅补足。

## H. FINAL_PREVIOUS_PLAN_RULE

新建下一轮时，创建 RPC 返回实际分配的编号后，在新轮详情只读取**同一 Space、`round_no = 新轮编号 - 1`** 的当前用户 participant entry 的「下一步计划」，作为只读参考；用户可见标题统一为「上一份计划」，空值文案为「上一份计划暂无内容」。这样并发创建不会把确认创建前读到的旧“最新轮”错当上一轮。不自动复制、不按日期找、不跳到更早有内容的轮次、不建立链图。之后始终以该轮编号读取上下文，日期更正不影响它。

## I. IMPLEMENTATION_SLICES

1. **Backend foundation / migration / DB tests**：在本地一份 additive forward patch 及 `supabase/schema.sql` 中建立两表、约束、读策略/判定函数、全部窄 RPC、模块开关扩展；数据库测试覆盖 participant 隔离、Shared 双人门槛、日期和编号并发、直接 API/ACL、leave/remove/rejoin 与 Space 删除。完成评审前不应用 Production。
2. **Entry save + filled status**：加窄的前端数据调用和内容/状态组件，验证四项可空、全空禁标记、相同内容幂等、修改后状态变化、错误/重试及非本人内容不可写；沿用第一片已定义的 RPC，不增第二套写模型。
3. **Module hub + Space-scoped history/create**：功能中心入口、Space eligibility、单 Space 倒序分页历史及 `+` 创建；明确目标与日期，处理 Shared 缺成员、模块关闭和过期请求。
4. **Detail responsive UI + previous plan**：Personal 单列、Shared 桌面并排/手机切换、固定高度滚动框、日期更正与「上一份计划」只读参考；不加入 Realtime。
5. **Integration + authenticated manual acceptance**：相关 DB/Node 回归、`npm run build`、代码审查及 docs 更新；先完成前端目标 backend/schema/RPC 兼容 gate。按项目已冻结的 backend-first rollout 和授权规则进行后续 Production 步骤；真实账号、两人、手机/PWA 验收由用户执行，不在本次 design freeze 执行。

## J. ACCEPTANCE_CRITERIA

- Personal 一人和 Shared 两人能各自创建；Shared 一人不能创建；同 Space 并发创建编号唯一且固定，日期更正不影响编号和上次计划。没有单次删除能力。
- 创建时 participant 固定。A/B 可看同轮双方内容而仅改自己；第三人加入后不能经 UI、表 SELECT 或 RPC 读取/补写旧轮。A leave/remove 后不能访问，B 保有双方历史；A 再加入后恢复旧轮访问。跨 Space、anon、非 participant 直接 API 均被拒绝。
- 四字段均可留空；全空显示未填写并禁标记；非空初次编辑、标记、再编辑、再标记的状态依次正确；相同内容重复保存不加版本。
- 关闭模块不删历史、不进正常选择器且所有写入被数据库拒绝；重开后原轮次恢复。整个 Shared Space 删除会清除回顾，成员 leave/remove 不清除。
- 首页显示 authoritative `共 N 篇回顾`，历史行仅显示日期、状态并按日期倒序；历史与详情均不显示 `round_no`。详情满足桌面/手机布局与固定高度内部滚动；「上一份计划」只取紧邻内部编号。无 Realtime 依赖。验证 0、1、超过一页的总数、Space 切换、新建后回到历史的总数刷新、空态、错误、分页、320px、键盘和用户执行的双账号/设备路径。
- 自动检查与部署状态必须分别记录，不能把本地设计、数据库测试或 UI 测试写成 Production/真实账号 PASS。

## K. SCOPE_GUARD

首版不做单次回顾删除、Realtime、scheduler、自动两周提醒或其他自动提醒、push reminder、语音、AI 总结、Excel 导出、复杂模板、归档、完成后锁定、generic content framework、generic permission framework、form builder、Shared Lists、Important Dates、Memo、Share / Projection、全站 Design System 重构、Shared 三人以上模式或跨 Space 混排。现有 Event、Task、Reminder、日历与其他模块行为保持原有语义。

## L. REMAINING_OPEN_DECISIONS

无阻止实现的产品或架构决策。字段长度、具体组件拆分、加载分页大小、提示文案等属于实现细节，在上述约束内确定；发现与 Production 后端真实状态不符时先按项目环境兼容 gate 停止验收并核对。
