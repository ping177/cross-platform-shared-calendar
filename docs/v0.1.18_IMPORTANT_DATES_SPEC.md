This document is the canonical product, data, permission, projection, reminder, lifecycle, and implementation-planning contract. v0.1.17 remains `CLOSED / PASS`. The user approved this Design Freeze and docs-only governance commit, not business implementation, Production writes, deployment, or push. ## 2. Repository evidence and reuse boundaries

- `supabase/schema.sql` already allows `important_dates` in the `space_modules` CHECK, but `set_space_module_enabled` permits only `tasks / review / lists`. No Important Date table, module page, projection, or reminder source is implemented.
- Tasks, Review, and Lists preserve records when disabled, exclude disabled Spaces from normal UI, and reject business mutations. Their historical SELECT remains authorized for current members; Review additionally requires historical participation. None currently has Push; Review/Lists have no Home or Calendar projection. Do not refactor them.
- `src/lib/module-availability.ts` and `src/components/ModuleHub.tsx` provide session-scoped eligibility hints. Reuse the [v0.1.16 entry convention](./DECISIONS.md): safe same-session view retention plus module-owned canonical reread, never mutation authority or persistent business cache.
- Home has independent Event/Task reads and section errors (`src/components/HomePage.tsx`, `src/lib/home-aggregation.ts`). Its existing five-row expansion and three-day Event window are not the Important Date top-three contract.
- Calendar reads complete canonical Event sources/exceptions and expands the visible range (`src/lib/aggregate-calendar.ts`, `src/App.tsx`). `src/lib/recurrence.ts` intentionally skips February 29 in non-leap years for Events; Important Dates require a separate small pure-date helper without changing Event semantics.
- Existing all-day presets, IANA conversion, subscriptions, Web Push, scheduler, claim and ledger concepts are reusable. `send-reminders` currently knows only ordinary/recurring Events; source-specific backend additions are required.
- `space_modules` has no Realtime publication. Shared Space deletion already cascades Space-owned data; its current confirmation in `SpaceManagementPage.tsx` lists only 日程和任务, omitting 回顾 and 清单.

## 3. Space ownership, eligibility, and create target

- Support Personal and Shared Spaces. `space_id` is the only ownership field. `created_by` is audit metadata, not ownership or edit authority.
- Reuse `space_modules(space_id,module_key,enabled)` with key `important_dates`. Missing/false means disabled. Existing and newly created Spaces do not automatically enable the module.
- Only a Space owner may toggle through the existing RPC's narrow allowlist extension. Ordinary members read module state without direct table writes.
- 功能中心 shows 重要日 iff at least one current-member Space enables it; all eligible Spaces disabled means no card. Unknown/error is not confirmed disabled.
- The module has its own filter: 全部空间 or one current-member, enabled Space. Default is 全部空间. It is independent of Calendar, Tasks, Lists, Review, and management selection.
- Freeze `CURRENT FILTER AS DEFAULT PRESELECTION, NOT OWNERSHIP AUTHORITY`: 全部空间 defaults to Personal; a specific eligible Space defaults to that Space. The visible form target can be changed and alone supplies the submitted ownership.
- Missing/disabled Personal or invalid specific target cannot silently select another Space. Require explicit valid selection or block save. Background filter changes do not rewrite an open form target. Revalidate current membership/module eligibility at submission; backend/RLS remains authoritative.
- Saved identity, including Space, remains immutable; no cross-Space move in v1.

## 4. Unified object and proposed persistence contract

Do not split countdown, anniversary, and count-up into object types or user-selectable display modes. User fields are name, optional Emoji, Space, date, repeat 每年 / 不重复, and an optional date-level Push setting when the reminder capability is ready.

One `important_dates` table is planned:

| Field | Contract |
| --- | --- |
| `id` | UUID primary key |
| `space_id` | Required FK to Spaces, `ON DELETE CASCADE` |
| `name` | Required trimmed single-line name, maximum 200 characters; existing validation style |
| `emoji` | Nullable, bounded optional Emoji; no image or icon catalog |
| `repeat_kind` | `annual / none` |
| `month`, `day` | Required valid Gregorian month/day |
| `year` | Optional canonical start year for annual; required year for none |
| `reminder_kind` | Nullable, only the two existing all-day presets |
| `time_zone` | One persisted valid canonical IANA timezone captured on creation |
| `reminder_schedule_changed_at` | Server-maintained schedule change marker |
| `created_by`, `created_at`, `updated_at` | Server-controlled audit metadata |

Month/day/year are the sole date representation; do not also persist a redundant date. 不重复 requires a complete valid YYYY-MM-DD. Annual without year allows February 29; annual with year requires a real start date in that year, so a February 29 anchor requires a leap year. Invalid dates must be rejected, not normalized by overflow.

Do not persist next occurrence, countdown, elapsed-day count, anniversary number, Past status, or projected Calendar rows. No Event FK, hidden Event, recurrence exceptions, series split, archive, or second ownership field.

## 5. Pure-date rules and future start-year eligibility

One small Important Date pure-date helper/contract must serve module list, Home, Calendar, and reminder occurrence discovery. SQL validation must enforce the same input/eligibility invariants. This is not a generic recurrence engine.

- Use Gregorian civil dates and date ordinals for differences; do not divide local-midnight milliseconds by 24 hours across DST. Avoid UTC parsing of YYYY-MM-DD shifting the display date.
- For annual without year, each year's resolved month/day is eligible. February 29 resolves to February 28 in non-leap years, and February 29 in leap years.
- For annual with year, **canonical start date = year + month + day**. There is no occurrence before that date. First legal occurrence is exactly the canonical start date; subsequent years follow annual resolution and the same February 29 fallback.
- Before canonical start: list shows a future countdown to the true start date, no negative count-up or fictional anniversary; Home ranks that true first occurrence; Calendar earlier years show nothing; Reminder has no eligibility for any fictional earlier annual occurrence.
- A previous-day reminder for the first legal occurrence may itself be due before the start date: the boundary governs occurrence identity, not removal of the frozen 前一天20:00 preset. Creation/edit past-due rules still apply.
- Next occurrence includes today and respects the start boundary. Annual records always have a next occurrence and never move to Past.
- With start year after start: `第 X 天 = civil-date difference + 1`; start date is Day 1. Calendar anniversaries use real resolved anniversary dates and year differences, never days/365. Start day is 第 1 天, not 0 周年.
- Annual without year shows only next occurrence/countdown; do not infer age or anniversary number. On occurrence day use 就是今天.
- 不重复: future countdown, today 就是今天, past Past section. 已过去 X 天 is elapsed date difference, distinct from inclusive 第 X 天.
- Display dates/today follow existing local Calendar civil-date semantics. Reminder instants use the saved object timezone; travel never rewrites the pure date or timezone.

Acceptance examples: a 2028-02-29 anchor has no 2027 occurrence, first occurs 2028-02-29, then 2029-02-28 (1 周年); a 2030-09-30 anchor does not generate 2026-09-30, and before start its next occurrence is 2030-09-30. All consumers must agree.

## 6. Module page and Emoji

- Full module page with existing module navigation and Sheet interaction patterns; no second navigation architecture.
- Current rows sort by next occurrence ascending with stable identity tie-breaks. Show Space context in aggregation.
- Annual with start year: primary 第 X 天, secondary 距 N 周年还有 X 天; on a positive anniversary date primary N 周年. Before start use the true-start countdown.
- Bottom 过去 section contains only expired non-repeat rows, defaults collapsed, shows original date and optionally 已过去 X 天. No Archive.
- Row opens Important Date's own view/edit Sheet. Delete requires explicit confirmation; no trash/undo.
- Emoji is optional. If absent, use one consistent default icon, reused in module list, Home, and Calendar. Use existing icon/style resources; no themes, covers, colors, or large icon library.

## 7. Home projection

Home adds a lightweight area, not another full module: at most three entries, next occurrence ascending, stable ties; exclude past non-repeat records. Count-up records rank by next occurrence, not elapsed days. No arbitrary three-day horizon or five-row expansion.

Source set is current membership intersected with enabled Important Date Spaces. No eligible Space means hide the area. Title / 查看全部 enters the full module. Record click follows Important Date's own interaction path. Examples: ❤️ 我们相识 · 第 1594 天; 🎂 妈妈生日 · 还有 12 天; ✈️ 川滇旅行 · 还有 18 天.

Use a module-specific complete source read, request guard, independent loading/error/retry, and derived top three. An Important Date failure must not fail existing Event/Task sections or be reported as empty success.

## 8. Calendar projection

- Important Date remains canonical; never copy/create hidden Event rows.
- Calendar's own filter selects visible Spaces; intersect those with Important Date module eligibility. Projection never changes ownership.
- Project annual dates only in the visible civil-date range, including the month view's 42-cell coverage; enforce canonical start boundary. Non-repeat projects only its exact date, including historical Calendar views.
- Use a distinct Important Date occurrence type carrying record ID, Space, and resolved occurrence date. Event and Important Date source types remain separate; merge only as needed for display.
- Reuse Emoji/default icon and a light 重要日 identifier within existing card styles. Include projections in day/month indicators without a new design system.
- Click must enter Important Date's own Sheet/path, never EventSheet or Event occurrence mutation RPCs. Projection is read-only; edits target the canonical Important Date.
- Keep source errors explicit; do not silently claim complete Calendar content after failed Important Date reads.

## 9. Disable semantics, permissions, and lifecycle

**关闭模块 ≠ 删除数据**. Disabling preserves records, reminder settings, and timezone; removes that Space from normal module availability, Home, and Calendar; denies business writes and suspends Push eligibility. Re-enable restores canonical records/settings without recreating data or introducing a historical replay queue.

Current Shared members may view/create/edit/delete any Important Date. Personal follows existing sole-owner/membership rules. Historical SELECT can remain current-member authorized while disabled, matching Tasks/Lists; normal UI has no disabled-history bypass. No Review-style participant snapshot.

RLS, constraints, column grants, identity guards, and locked backend checks are authoritative. Important Date writes and toggle must serialize at the existing Space advisory/row-lock boundary with lifecycle/claim and revalidate membership/module state after locking. Deny invalid targets and broad runtime privilege bypasses.

- Leave/remove: retain Space-owned Important Dates, immediately revoke departing member access/new reminder eligibility. Do not cascade through a member or created_by FK.
- Join: current members can read objects and qualify for subsequent reminders; ownership transfer changes neither records nor settings.
- Delete Important Date: confirmed hard delete, remove projections and stale send eligibility, retain independent ledger audit.
- Delete Shared Space: FK cascade removes Important Dates; preserve existing Space deletion semantics and RPCs. No new lifecycle cleanup framework.
- **Bounded Shared Space delete copy correction is authorized in Slice 1**: permanent deletion copy must accurately include 日程、任务、回顾、清单、重要日. Correct existing confirmation copy only; do not rewrite Space Management, alter deletion semantics, refactor lifecycle RPCs, or polish unrelated UI.

## 10. Date-level reminder settings and publication gate

Reuse current all-day Event UX and stored preset names:

| UI | Stored value |
| --- | --- |
| 不提醒 | `null` |
| 当天08:00 | `all_day_same_day_08` |
| 前一天20:00 | `all_day_previous_day_20` |

New Important Dates default to 当天08:00 **once the complete reminder capability is available**. Slice 1 may prepare reminder fields/constraints, but if deployed independently it must keep Reminder UI unavailable/unexposed and keep pre-capability records unenabled (`reminder_kind = null`). Do not auto-enable those historical records when Slice 2 arrives. No setting UI that promises delivery from an absent sender.

**Reminder publication gate:** candidate discovery, due calculation, ledger, source-specific claim, pre-send membership/module/source/subscription revalidation, Push send path, idempotency tests, and old Event regression must all pass, with the actual target backend capability gate verified, before publishing reminders as a feature users can rely on. Passing schema tests or storing a preset alone does not open this gate.

Persist one valid canonical IANA timezone captured from the creating browser/PWA; invalid detection fails explicitly, without guessed UTC. Preserve it on edits, device changes, travel, and disabling reminders. No profile timezone service or device orchestration. `resolved occurrence date + preset + time_zone` derives one UTC due instant using existing native Intl conversion/DST rules.

Shared members share one reminder setting and canonical instant; one member changing the preset changes it for everyone. No 09:00, custom time, extra advance-day counts, multiple reminders, or per-member preferences. Retain existing newly-past skip, approximately ten-minute infrastructure grace, and best-effort delivery semantics. Existing notification click opens the app; no new notification deep-link requirement.

## 11. Reminder recipients, backend delta, and idempotency

Personal sends to the current sole owner/member; Shared sends to all current members with valid active subscriptions. Current membership at claim/send time is authoritative, not creation-time membership. Module disabled, deleted/changed source, stale schedule, removed member, disabled/expired subscription means no new send eligibility.

Extend existing `send-reminders` with one explicit Important Date source branch:

1. Stable bounded candidate pages, enabled filtering, and explicit overflow detection; no silent truncation.
2. The same pure-date resolver projects only a bounded occurrence window covering same-day, previous-day, grace, year boundaries, February 29, and canonical start eligibility.
3. Reuse date-level preset/timezone conversion. A small helper extracted from existing all-day calculation must preserve old Event outputs, not require fabricated Event objects.
4. Resolve current memberships and valid subscriptions; keep one shared run budget (existing 50 selected tasks, five workers, 95-second claim cutoff), rather than separate per-source send budgets/schedulers.
5. Add service-role-only `claim_important_date_reminder_delivery` with hardened search_path, revoked public/anon/authenticated EXECUTE, existing Space lock boundary, and post-lock source/member/module/subscription/marker/grace checks. Preserve raw PostgreSQL timestamp precision.
6. Revalidate membership, module, source schedule and subscription immediately before send using a narrow canonical backend check; failure means no Push. Exact check wiring is a Slice 2 implementation detail, not a generic eligibility framework.
7. Reuse Web Push, subscription retirement and ledger finalization. Namespace the opaque notification tag by Important Date source, occurrence date, and due instant. Already-in-flight provider requests cannot be recalled after a concurrent membership/module change; do not promise retractable Push.

Server-maintained reminder schedule marker changes on repeat/date/year/preset/timezone edits; name/Emoji-only changes do not create a new due identity. Stale snapshots must be rejected. Unchanged delivery identity must never send again.

Ledger extension contract: add nullable `important_date_id`, allow nullable legacy `event_id`, and enforce exactly one source identity. Important Date `occurrence_date` is required. Extend the existing same-named `reminder_deliveries_occurrence_identity_key` atomically to `UNIQUE NULLS NOT DISTINCT (event_id,important_date_id,occurrence_date,subscription_id,due_at)`.

Existing ordinary/recurring Event rows get `important_date_id = null`, retain the same effective identity, and retain existing claim signatures and `ON CONFLICT ON CONSTRAINT` usage. Do not store an Important Date ID in event_id. Merely adding another index while leaving the old nulls-not-distinct constraint unchanged would collide across Important Date IDs and is invalid. No business-object/member/subscription FK on ledger; audit survives deletion. Preserve service-role-only ledger privileges and absence of browser/Realtime access.

## 12. Loading, Realtime, and navigation persistence

**No Realtime in v1**, no polling substitute or always-on subscription. Reuse Review's bounded reread model: entry/return, successful mutations, focus/reconnect, local module changes, explicit retry, and Calendar range changes. Refresh derived day values at civil-date rollover. Another continuously open Shared client need not update immediately; backend membership/module/send checks remain authoritative.

Reuse current session module availability and module-owned canonical reads. A safe user/scope-bound in-memory display snapshot may preserve ordinary Hub re-entry while refreshing in the background; recompute time-dependent values. Clear affected data on confirmed membership/eligibility loss, auth switch/sign-out, or relevant mutation rejection. Failed reads are errors, not proof of deletion. No persistent frontend business cache, global store, query/repository abstraction, or generic loader.

Add one Important Date module navigation target to the existing strict parser/session-storage contract; retain only page identity and stable IDs. Sheet editing does not require a second detail navigation architecture. Restore only after eligibility validation; missing record returns to the valid module list, no eligible Space returns to 功能中心. Home/Calendar clicks use the same own-object interaction path. No drafts/business rows in persistent navigation storage.
