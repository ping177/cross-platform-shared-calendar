# v0.1.6 Recurring Events Specification

## Status and scope

This is the implementation specification for v0.1.6 recurring events. It is
based on [the architecture investigation](./v0.1.6_RECURRING_EVENTS_INVESTIGATION.md).
It defines the data contract and behavior only; it does not execute a migration
or modify the application, Supabase, RLS, or Realtime configuration.

### Objective

Users can create a shared or personal event that repeats daily, weekly, monthly,
or yearly. The calendar shows a bounded set of generated display occurrences,
while Supabase stores exactly one source `events` row for the series.

### In scope

- A nullable `events.recurrence_rule` JSON/JSONB value.
- Daily, weekly, monthly, and yearly recurrence.
- Whole-series create, display, edit, and delete.
- Frontend-only, visible-range-bounded occurrence expansion.
- Existing shared/personal ownership, RLS, and events Realtime behavior.

### Out of scope

- RFC 5545 RRULE parsing or interchange.
- One-occurrence edits/deletes, skipped dates, detached occurrences, or split
  series.
- A recurrence/occurrence table, RPC/API expansion, or materialized
  occurrences.
- Series end dates/counts in v0.1.6.
- Reminders (v0.1.7) and general UI enhancement work (v0.1.8).

## 1. `recurrence_rule` JSON schema

### Storage contract

`events.recurrence_rule` is nullable.

- `null` means the existing one-off event behavior; all current events remain
  fully compatible.
- A non-null value is a JSON object conforming to the v1 schema below.
- The proposed database storage type is `jsonb`; it preserves structured data,
  supports structural validation, and does not require a recurrence table.
- The source event's `starts_at`, `ends_at`, `all_day`, `scope`, and
  `owner_user_id` remain authoritative. The rule never duplicates ownership or
  event content.

### Canonical JSON examples

Daily at the source event's local time:

```json
{
  "version": 1,
  "frequency": "daily",
  "interval": 1,
  "time_zone": "Asia/Shanghai"
}
```

Every second week on Monday, Wednesday, and Friday:

```json
{
  "version": 1,
  "frequency": "weekly",
  "interval": 2,
  "days_of_week": [1, 3, 5],
  "time_zone": "Asia/Shanghai"
}
```

Monthly on the last day of the month:

```json
{
  "version": 1,
  "frequency": "monthly",
  "interval": 1,
  "day_of_month": "last_day",
  "time_zone": "Asia/Shanghai"
}
```

Every year on July 17:

```json
{
  "version": 1,
  "frequency": "yearly",
  "interval": 1,
  "month": 7,
  "day": 17,
  "time_zone": "Asia/Shanghai"
}
```

### JSON Schema (Draft 2020-12)

This schema describes the required shape. The later database migration should
enforce an equivalent narrow validation rule; PostgreSQL does not apply JSON
Schema automatically.

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "cross-platform-shared-calendar/recurrence-rule-v1",
  "title": "Recurring event rule v1",
  "type": "object",
  "additionalProperties": false,
  "required": ["version", "frequency", "interval", "time_zone"],
  "properties": {
    "version": { "const": 1 },
    "frequency": { "enum": ["daily", "weekly", "monthly", "yearly"] },
    "interval": { "type": "integer", "minimum": 1, "maximum": 365 },
    "time_zone": {
      "type": "string",
      "minLength": 1,
      "description": "Canonical IANA time-zone name, for example Asia/Shanghai."
    },
    "days_of_week": {
      "type": "array",
      "minItems": 1,
      "maxItems": 7,
      "uniqueItems": true,
      "items": { "type": "integer", "minimum": 1, "maximum": 7 }
    },
    "day_of_month": {
      "oneOf": [
        { "type": "integer", "minimum": 1, "maximum": 31 },
        { "const": "last_day" }
      ]
    },
    "month": { "type": "integer", "minimum": 1, "maximum": 12 },
    "day": { "type": "integer", "minimum": 1, "maximum": 31 }
  },
  "allOf": [
    {
      "if": { "properties": { "frequency": { "const": "weekly" } } },
      "then": {
        "required": ["days_of_week"],
        "not": { "anyOf": [{ "required": ["day_of_month"] }, { "required": ["month"] }, { "required": ["day"] }] }
      },
      "else": { "not": { "required": ["days_of_week"] } }
    },
    {
      "if": { "properties": { "frequency": { "const": "monthly" } } },
      "then": {
        "required": ["day_of_month"],
        "not": { "anyOf": [{ "required": ["days_of_week"] }, { "required": ["month"] }, { "required": ["day"] }] }
      },
      "else": { "not": { "required": ["day_of_month"] } }
    },
    {
      "if": { "properties": { "frequency": { "const": "yearly" } } },
      "then": {
        "required": ["month", "day"],
        "not": { "anyOf": [{ "required": ["days_of_week"] }, { "required": ["day_of_month"] }] }
      },
      "else": { "not": { "anyOf": [{ "required": ["month"] }, { "required": ["day"] }] } }
    },
    {
      "if": {
        "required": ["month"],
        "properties": { "month": { "enum": [4, 6, 9, 11] } }
      },
      "then": { "properties": { "day": { "maximum": 30 } } }
    },
    {
      "if": {
        "required": ["month"],
        "properties": { "month": { "const": 2 } }
      },
      "then": { "properties": { "day": { "maximum": 29 } } }
    }
  ]
}
```

In addition to the structural schema:

- `time_zone` must be accepted by the application's IANA time-zone validator.
- `days_of_week` is stored in strictly ascending order to make a rule canonical.
- The UI creates the initial canonical values from `starts_at`: daily has no
  day selector; weekly defaults to the source weekday; monthly defaults to the
  source day of month; yearly defaults to the source month and day.
- `interval` has a schema maximum of 365 only to prevent accidental pathological
  inputs. It means a number of calendar units, not a duration in seconds.

## 2. Frequency rules

All recurrence calculations use the event's local civil date and wall-clock
time in `recurrence_rule.time_zone`. The source event itself is always the first
occurrence, even if it would not otherwise match a weekly/monthly/yearly
selector.
No rule has a series end in v0.1.6; generation is instead range-bounded.

| Frequency | `interval` meaning | Required selector | Generated dates |
| --- | --- | --- | --- |
| `daily` | Every N calendar days after the source local date. | None. | Source date plus 0, N, 2N… days. |
| `weekly` | Every N calendar weeks, anchored to the Monday–Sunday week containing the source local date. | `days_of_week`. | In eligible weeks, each selected weekday at the source wall-clock time, excluding candidates before the source start. |
| `monthly` | Every N calendar months, anchored to the source year/month. | `day_of_month`. | In eligible months, the selected numeric day when it exists, or the final local day for `last_day`. |
| `yearly` | Every N calendar years, anchored to the source year. | `month` and `day`. | In eligible years, the selected month/day when that date exists. |

### `days_of_week`

`days_of_week` is permitted only for `weekly`:

| Value | Day |
| --- | --- |
| `1` | Monday |
| `2` | Tuesday |
| `3` | Wednesday |
| `4` | Thursday |
| `5` | Friday |
| `6` | Saturday |
| `7` | Sunday |

The array contains at least one unique value and must be ascending. For
example, an event starting Tuesday with `days_of_week: [1, 3]` has no generated
Monday occurrence before its source start, but may generate that Wednesday if
the source week is eligible.

### `day_of_month`

`day_of_month` is permitted only for `monthly`:

- An integer from `1` through `31` means that exact calendar date.
- `"last_day"` means the final calendar date of every eligible month.
- The numeric option and `"last_day"` are deliberately different; the latter
  is the only way to request month-end behavior.

### `month` and `day`

`month` and `day` are permitted only for `yearly`:

- `month` is an integer from `1` through `12`.
- `day` is an integer from `1` through `31`.
- The pair means that exact calendar date in each eligible year; it is not a
  month-relative rule and does not support `"last_day"`.
- The schema rejects impossible month/day pairs such as April 31 and February
  30. February 29 remains valid and is skipped in non-leap years. The UI
  defaults both fields from `starts_at`.

## 3. Occurrence generation

### Source versus display occurrence

An `events` row is a **source event**, never a row per occurrence. The frontend
projects it into zero or more **display occurrences** for one calendar range.
A display occurrence is not persisted and must carry at least:

```ts
type CalendarOccurrence = {
  occurrence_id: string; // `${source_event_id}:${occurrence_starts_at}`
  source_event_id: string;
  occurrence_starts_at: string; // generated absolute ISO instant
  occurrence_ends_at: string | null;
  source_event: CalendarEvent;
};
```

The UI uses `occurrence_id` for React keys, but every edit/delete operation
uses `source_event_id`. A generated occurrence ID must never be sent as an
`events.id` filter.

### Generation algorithm

For a requested display range `[range_start, range_end]`:

1. If `recurrence_rule` is `null`, project exactly one occurrence from the
   source event.
2. Convert `starts_at` to the rule's `time_zone` and retain its local date and
   wall-clock time as the series anchor.
3. Generate only candidate local dates prescribed by the frequency and
   selectors, including `month` + `day` for yearly rules. Convert each candidate
   with the anchor wall-clock time back to an absolute instant in `time_zone`.
4. Preserve the source event's duration: if `ends_at` exists, each generated
   end is `occurrence_start + (ends_at - starts_at)`; otherwise it is `null`.
5. Retain an occurrence when its `[occurrence_start, occurrence_end]` intersects
   the requested display range. A null end is treated as equal to its start.
6. Sort retained occurrences by generated start instant, then source event ID.

The source start occurrence is included once only. If regular generation would
produce the same timestamp, deduplicate it by `occurrence_id`.

### Mandatory generation limit

Expansion must be finite even for a never-ending rule:

- The range is derived from the active UI, not from all time.
- Today expands only the selected local calendar day.
- Week expands Monday 00:00 through Sunday 23:59:59.999 of the selected week.
- Month expands the complete 42-cell calendar grid, including visible days from
  adjacent months, because those cells show event markers today.
- The implementation must set a hard per-source-event cap of **500 generated
  candidates** for one expansion call. Reaching the cap is an error path: stop
  expansion, report a safe UI error, and do not silently return a partial list.

The existing client currently reads all source events in a space. v0.1.6 must
not replace this with unbounded generated state; only the projected occurrence
array is range-limited.

## 4. Monthly edge cases

| Rule | February | 30-day month | 31-day month |
| --- | --- | --- | --- |
| `day_of_month: 28` | Occurs on Feb 28. | Occurs on the 28th. | Occurs on the 28th. |
| `day_of_month: 29` | Occurs only on Feb 29 in leap years; non-leap February is skipped. | Occurs on the 29th. | Occurs on the 29th. |
| `day_of_month: 30` | February is skipped. | Occurs on the 30th. | Occurs on the 30th. |
| `day_of_month: 31` | February is skipped. | The month is skipped. | Occurs on the 31st. |
| `day_of_month: "last_day"` | Feb 28, or Feb 29 in a leap year. | The 30th. | The 31st. |

Rules never clamp a numeric day to a shorter month. For example, a rule for the
31st does **not** become the 30th in April or the 28th/29th in February. Users
who want “the last day of every month” select `"last_day"` explicitly.

The monthly interval is counted by year/month arithmetic from the source month;
skipped invalid dates do not shift the interval. For example, a two-month rule
anchored in January considers March, May, July, and so on, even if an eligible
month lacks the requested day.

For yearly rules, the interval is counted by calendar-year arithmetic from the
source year. A rule with `month: 2` and `day: 29` generates only leap-year
occurrences in eligible years; skipped non-leap years do not shift the interval.

## 5. Timezone policy

### Storage

- Continue storing `events.starts_at` and `events.ends_at` as PostgreSQL
  `timestamptz` absolute instants. Do not change existing columns or reinterpret
  existing one-off event data.
- Each non-null rule includes a required IANA `time_zone` string, such as
  `Asia/Shanghai`. This is the series' authoritative recurrence timezone.
- The source event's local date and wall-clock time in that timezone are the
  recurrence anchor. Repeated 09:00 means 09:00 in this timezone, not “every
  24 hours from the stored UTC instant.”

### Display

- Generate absolute occurrence instants using the authoritative series timezone.
- Render event date/time with the viewer device's local timezone, preserving the
  current app behavior for both one-off and recurring events.
- Therefore two members in different timezones may see the same timed
  occurrence on different local calendar dates/times; it is still one identical
  instant. The recurrence rhythm itself remains stable in the series timezone.
- `all_day` remains a presentation flag in v0.1.6. Recurring all-day events use
  the source local date in the series timezone as their recurrence anchor and
  display as “全天”; v0.1.6 does not introduce a separate date-only storage
  model.

### DST behavior

The target production timezone is commonly `Asia/Shanghai`, which currently
has no DST transitions, but the schema permits valid IANA zones. For a zone
with DST:

- a nonexistent local time in a spring-forward gap resolves to the first valid
  local time after the gap;
- an ambiguous local time in a fall-back overlap resolves to the earlier
  occurrence/offset;
- this behavior must be implemented by a timezone-aware date utility and tested
  before claiming support for DST-observing zones.

## 6. Series semantics

### Creation

Creating a recurring event inserts one `events` source row with its rule. The
existing insert policy and owner trigger continue to control `space_id`,
`created_by`, `scope`, and `owner_user_id`.

### Edit entire series

Opening any display occurrence opens its source event. Saving updates the source
row and applies the changed title, description, start/end, all-day state, or
rule to the entire series. The UI must say “编辑整个重复日程” (or equivalent),
not imply that a single date can be changed.

Existing authorization remains unchanged:

- Any space member can edit a shared series.
- Only `owner_user_id` can edit a personal series.
- A non-owner personal series is display-only, including every generated
  occurrence.

### Delete entire series

Deleting any display occurrence deletes its source row and removes the complete
series. The UI must say “删除整个重复日程” and require the same confirmation used
for a normal event deletion if/when confirmation UX exists.

### Unsupported operations

The following must not be presented in the UI or simulated through hidden data:

- edit/delete only this occurrence;
- skip this occurrence;
- change this and future occurrences;
- detach an occurrence into a one-off event;
- change the event's stable ownership/identity fields.

## 7. Migration checklist (plan only)

No item in this section is authorized for execution by this specification.

1. Review this specification and the investigation document; confirm that
   v0.1.6 intentionally has no series end, exceptions, or materialization.
2. Write a new versioned file under `supabase/patches/`; do not rerun
   `supabase/schema.sql` against an existing environment.
3. Add a nullable `recurrence_rule jsonb` column without a default. `NULL` is
   the legacy-compatible one-off value, so no historical backfill is required.
4. Add a narrow database validation constraint/trigger equivalent to the v1
   schema: object or null, supported frequency, valid selector relationship,
   positive bounded interval, and valid IANA timezone. Run a read-only
   preflight first and validate the constraint before production rollout.
5. Update the canonical `supabase/schema.sql` only after the patch is approved,
   so fresh installs match the deployed schema. Do not alter existing event
   identity fields, `event_ends_after_start`, or owner-shape constraints.
6. Confirm that `events_select_member`, `events_insert_member`,
   `events_update_member`, and `events_delete_member` are byte-for-byte or
   behaviorally unchanged. No recurrence-specific RLS policy is required.
7. Keep the `events` Realtime publication and `REPLICA IDENTITY FULL` unchanged;
   a rule edit is an ordinary source-row update.
8. Apply the approved patch once per target environment, then record the
   preflight, schema, RLS, trigger, and two-account verification results in the
   appropriate testing and development-log documents.

## Implementation sequence and acceptance criteria

Implementation begins only after human review of this specification.

1. **Schema contract (Small)**
   - Add the additive patch and matching fresh-install schema definition.
   - Verify existing events still select and mutate as one-off events.
   - Verify RLS and owner-trigger behavior is unchanged.

2. **Pure recurrence projection (Medium)**
   - Add a separate source-event/occurrence type and deterministic range
     expansion helper.
  - Test daily, weekly, monthly, yearly, interval, range intersection, the
    500-cap, leap February, 30th/31st, `last_day`, duration, and source
    deduplication.
   - Do not add a testing dependency without explicit user approval; the current
     project has no test script/framework.

3. **Calendar integration (Medium)**
   - Feed projected occurrences into today, week, and all 42 month-grid cells.
   - Keep raw source rows as the only mutation inputs and retain events Realtime
     reload behavior.
   - Verify a repeated event appears only in the selected visible range.

4. **Series form/detail semantics (Medium)**
   - Add rule creation/editing and clear whole-series copy.
   - Verify shared-series and personal-owner mutation permissions plus
     non-owner personal read-only behavior.
   - Run `npm run build` and the documented two-account Supabase/Realtime
     smoke checks.

## Open questions and implementation risks

No unresolved product decision blocks this specification. The following are
implementation decisions that must be closed before coding:

- The project currently has no test framework and no timezone utility. Decide
  whether the supported browser/runtime features are sufficient for IANA/DST
  calculations or whether to add a dependency; adding one requires prior user
  approval.
- The 500-candidate guard is deliberately conservative. Confirm the desired UI
  error copy and observability behavior before implementation.
- A future need for a series end date/count or any per-occurrence exception is
  a v0.1.7+ data-model decision. It must not be added opportunistically to the
  v0.1.6 rule shape.

## Documentation verification

This document is complete when it supplies a machine-readable rule shape,
unambiguous generation and month-end behavior, explicit timezone/series
semantics, and a non-executing migration plan. Documentation-only verification
is `git diff --check`; no build is required until code changes.
