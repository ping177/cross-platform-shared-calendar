## 1. Objective and status

Shared Lists adds a Space-owned module for small collections of items that current members maintain together. It supports both Personal and Shared Spaces and keeps Lists distinct from Tasks: Lists have no assignee, due date, reminder, priority, or task status history.

This document freezes product semantics, the bounded data and permission design, Realtime behavior, implementation slices, and acceptance strategy. Slice 1 DB foundation passed local verification and Production rollout/postflight. Frontend Slices 2–4 and authenticated Lists acceptance have not started. The existing `space_modules` constraint accepts `lists`, and the deployed owner-only toggle RPC allows it without enabling it by default.

Next action: v0.1.15 Slice 2 Overview / Ownership implementation planning / preflight.

## 2. Space ownership and eligibility

- A List belongs to exactly one Space. Space is the ownership boundary; created_by is audit metadata only and never grants or limits editing.
- Personal and Shared Spaces may independently enable Lists through the existing per-Space module model.
- A module row that is absent or disabled means Lists is unavailable in normal UI. Existing List data remains stored and becomes visible again after re-enabling.
- Normal reads show only Spaces where the current user still has membership and Lists is enabled. Database authorization remains authoritative.
- Shared Space current members jointly create, edit, complete, reorder, and delete Lists, Sections, and Items.
- A member leaving or being removed does not delete their created content. Ownership transfer does not change content. Deleting the Space cascades through Lists, Sections, and Items.

## 3. Overview, filter, and creation target

- The Lists module overview defaults to 全部空间 and aggregates Lists from all Spaces where the current user has membership and Lists is enabled.
- listFilter is module-local and independent of selectedSpaceId, calendarFilter, taskFilter, and Review Space selection. Choices are 全部空间, Personal Space, or one eligible Shared Space.
- All Spaces view labels each List with its source Space. A single-Space view may omit the repeated label.
- The overview has 进行中 and 已完成 groups. 已完成 is collapsed by default. Both groups sort by List created_at descending, then id descending for deterministic ties.
- The overview displays each List name and progress as 已完成 X / Y, computed from current Items.
- New List opens a lightweight Sheet containing only the List name and an explicit Space target. The default target is the user's Personal Space. The user may actively select another eligible Shared Space.
- Creation eligibility is current membership plus Lists enabled. The Sheet never derives ownership from selectedSpaceId, calendarFilter, taskFilter, or listFilter. It never silently redirects to a Shared Space. If the Personal Space is unavailable or Lists is disabled there, the user must choose an eligible target explicitly or cannot create.
- Normalize the name by trimming whitespace, reject blank names, and cap it at 200 characters, matching the existing Task title limit. There is no description, note, color, cover, deadline, owner, template, reminder, or notification setting.

## 4. List completion

A List is completed exactly when it has at least one Item and every Item is completed:

    totalItems > 0 AND completedItems == totalItems

- An empty List is active.
- A List containing Sections but no Items is active.
- Sections have no checkbox or completion state and do not participate independently.
- Adding an incomplete Item or reopening any Item makes the List active again.
- Completed Lists remain openable and editable. Completed does not mean archived.
- Do not persist a completed flag, completed_at, progress counter, archive state, or duplicate aggregate field.

## 5. Canonical data model

Use three relational tables only:

    lists → list_sections → list_items

No JSON tree, polymorphic parent-item rows, recursive hierarchy, or unlimited nesting.

| Table | Frozen fields |
| --- | --- |
| lists | id, space_id, name, created_by, created_at, updated_at |
| list_sections | id, list_id, name, sort_order, created_by, created_at, updated_at |
| list_items | id, list_id, space_id, nullable section_id, content, completed, sort_order, created_by, created_at, updated_at |

Schema invariants:

- UUID primary keys use the existing database default convention.
- lists.space_id references spaces.id with ON DELETE CASCADE. Lists are owned by their Space, not by created_by.
- list_sections.list_id references lists.id with ON DELETE CASCADE.
- list_items.list_id and list_items.space_id reference the matching parent List through a composite foreign key. The parent must have a corresponding unique key for the referenced pair.
- list_items.space_id is the one intentional technical redundancy. Retain it only with the composite foreign key that proves it matches the parent List. It routes overview Realtime by Space; it is not a second ownership field.
- list_items.section_id is nullable. NULL means ungrouped. A non-null section must belong to the same list_id, enforced by a composite foreign key to list_sections.
- Deleting a List cascades to its Sections and Items. Deleting a Section cascades to its remaining child Items at the FK level; the user-facing preserve-items operation first moves those Items to NULL section_id in the atomic RPC.
- created_by is immutable audit metadata, never an authorization boundary. Store it as a UUID snapshot without a profile or membership FK that could delete or block Space-owned business data when a user or membership changes.
- created_at and updated_at follow existing timestamp conventions. updated_at is maintained by the existing timestamp-trigger pattern.
- List name, Section name, and Item content are trimmed, nonblank single-line text with a 200-character limit. Quantity is part of content text, for example “牛奶 × 2”.

Do not add description, note, color, cover, deadline, owner/assignee, manual completion, archive, template, notification preferences, updated_by, or activity-log fields.

## 6. Sections and Items

Sections are optional grouping headings. A List can contain ungrouped Items and grouped Items at the same time. Ungrouped Items appear first, without an “未分组” heading.

Sections support create, rename, delete, manual ordering, and UI-local collapse. Collapse state is not written to the database, shared with another member, or restored after reload. A collapsed Section may show derived progress such as 衣物 3 / 8.

Items contain content, completion state, and canonical sort order. Shared Space members can add, edit, delete, complete, reopen, and reorder them regardless of created_by. The UI does not display authors.

## 7. Section and Item interactions

- At the top of List detail, ＋ 添加一项… creates an ungrouped Item.
- At each Section bottom, ＋ 添加一项… creates an Item in that Section.
- Successful quick-add immediately persists, clears the input, retains focus, and accepts the next entry with Enter or Add. Do not open a Sheet per Item.
- Item editing uses inline or a very small edit state, not a large editor framework.
- ＋ 添加分组 creates a Section inline. Enter creates it without navigation. Section names support quick inline rename.
- Completed Items remain in their original Section. Within each Section, active Items appear before a default-collapsed 已完成 group. Ungrouped Items use the same active/completed behavior without an extra heading.
- Whole-Section collapse, completed-Item folds, and overview completed-List collapse are UI-local state only.
- Delete one Item immediately with no confirmation. Deleting a whole List requires a two-step confirmation that identifies the List and its Space both times. Deleting a non-empty Section offers exactly the two choices frozen below.

### Non-empty Section deletion

“仅删除分组” atomically deletes the Section and moves its Items to the ungrouped region. Preserve the Items' relative order within that Section and append the entire ordered group to the end of the existing ungrouped order. The backend RPC assigns deterministic canonical sort_order values in the same transaction.

“删除分组及其中内容” atomically deletes the Section and every Item in it. Empty Sections can be deleted directly. The frontend must not perform a multi-step cleanup sequence.

## 8. Canonical ordering

Use deterministic integer/bigint sort_order. No fractional positions, CRDT, OT, global advisory locks, or collaborative ordering framework.

- Sections have a canonical order within the List.
- Items have a canonical order within their current Section or the ungrouped region.
- Completion is presentation state only. Completing or reopening an Item never changes canonical sort_order.
- Completed folds partition display; they do not rewrite stored order. Reopening an Item restores its original relative position.
- New Sections and Items append to the end of their canonical region.
- Moving Items from a deleted Section to ungrouped appends them as an ordered block, preserving their relative order.
- Reorder writes use narrow backend-owned transactional RPCs. The RPC locks the parent List row, validates the complete current target set, deterministically renumbers in one transaction, and rejects stale requests so the client can reload.
- Competing reorder RPCs serialize on that List. The last successful request wins when its submitted set is still current. No ordering request may silently omit a concurrent insertion or deletion.
- Active and completed Item folds retain one canonical sequence. Reordering one displayed completion group changes the slots occupied by that group while preserving the other group's slots, then renumbers deterministically.

Contiguous integer positions are the v1 choice. Sparse or fractional ordering reduces writes for a move but introduces collisions, precision/rebalance rules, and more concurrency cases without a demonstrated need. Do not optimize for very long Lists before measuring real use.

## 9. Drag and mobile interaction

Item drag reorder is a v0.1.15 product requirement within the ungrouped region and within the same Section. Up/down controls may serve accessibility, keyboard, or fallback use and may be an implementation stepping stone; they cannot silently replace the intended drag interaction in final acceptance.

Cross-Section Item drag is deferred / nice-to-have. Cross-List and cross-Space drag are out of scope.

Section drag is a target only while the bounded mobile implementation remains simple. If Slice 4 validation shows it materially increases touch/PWA complexity, explicitly defer Section drag without blocking v0.1.15.

The repository has no drag dependency. Do not install one during this Design Freeze. Slice 4 must validate touch scrolling, drag handles, keyboard/accessibility fallback, cancellation, and mobile reorder. Native HTML5 drag alone is insufficient for touch. A small mature touch-capable dependency may be evaluated later; dependency approval remains required before installation.

## 10. Permissions and mutations

Database membership, Space ownership, module enablement, RLS, constraints, triggers, and RPC checks are the security boundary. Realtime subscriptions never grant permission.

- List read: current Space member. Historical rows remain readable through the existing module pattern when Lists is disabled, while normal UI hides disabled Spaces.
- List write: current Space member and Lists enabled.
- Section and Item read/write inherit the parent List's Space and module state.
- created_by is set from the authenticated actor at creation and retained for audit only. It does not restrict edits or deletes.
- Ordinary Item content changes may use direct table writes under column grants and RLS. Completion/reopen uses the narrow `set_list_item_completed(item_id, completed)` RPC so a List row lock serializes completion-group changes with reorder. Single-Item deletion uses a narrow RPC to compact canonical order under the same List lock.
- List deletion, Section deletion in either mode, and ordering changes are narrow backend-owned RPCs because each enforces a multi-row invariant.
- Never use frontend per-row cleanup for List/Section deletion.

## 11. Realtime

Realtime is notification-to-reread. Committed database rows remain canonical.

Overview subscriptions cover current eligible Spaces and relevant List and Item changes. Item changes update derived progress after canonical reread. Detail subscriptions cover the current List's lists, list_sections, and list_items changes. Unmount overview subscriptions while detail is active; remove channels when the user leaves the view or changes target.

Reuse the existing Supabase subscription lifecycle, Space filtering, request guards, and reload/reconcile patterns. Reconnect triggers eligibility revalidation and canonical reread. Avoid duplicate subscriptions and stale responses.

The space_modules table is not currently in the Realtime publication. Add only the smallest compatible module-state signal needed to refresh Lists eligibility; do not redesign generic module synchronization. Revalidate membership and module eligibility on opening Lists, browser/app focus, Realtime reconnect, and failed/rejected mutations that may indicate lost eligibility. If eligibility is lost, clear stale Lists state, stop its subscriptions, and return to a valid Lists state. Do not add a perpetual Lists-specific membership polling loop.

Filtered DELETE delivery under Supabase Realtime + RLS + REPLICA IDENTITY FULL is an implementation and dual-account acceptance checkpoint. Schema/publication metadata alone is not proof. If filtered DELETE delivery fails in real two-account behavior, stop and reassess the smallest synchronization route before adding workarounds.

Personal Spaces use the same read and sync pattern. Membership/module state is revalidated at lifecycle boundaries; it is not a client-side permission source.

## 12. Bounded concurrency contract

Guarantee:

- no corrupted or cross-parent relational state;
- legal membership/module state at the database boundary;
- deterministic canonical order;
- eventual convergence to committed database state.

Specific behavior:

- Concurrent Item inserts serialize position assignment on the parent List. Both valid Items remain.
- Same-Item text or completion conflicts may use last-successful-write semantics. Completion writes an explicit boolean, not a toggle computed from stale local state.
- Completion/reopen and reorder acquire the parent List lock before Item rows. Direct Item content edits remain allowed, but direct `completed` updates are denied; a reorder therefore validates the complete current completion group under the shared lock order.
- If one member deletes an Item while another edits it, the edit affects zero rows or fails; reread and close the missing Item editor.
- Concurrent reorders serialize on the parent List row. A stale ID set fails and reloads rather than overwriting a new row.
- Section deletion and Item creation in that Section serialize on the parent List lock. The committed Section-delete choice determines whether an existing Item is moved or deleted; a later insert targeting a removed Section fails its FK.
- List deletion and child creation/reorder are resolved by parent locking and FK integrity. The transaction that observes the parent gone fails; a completed List delete cascades all descendants.
- Realtime events prompt canonical reload and reconciliation. No complex conflict UI is required.

Do not use global locks, collaborative merge algorithms, or updated_at guards for ordinary v1 Item text/completion edits.

## 13. Aggregation and performance

Overview progress and completion are derived from real Items. Initially, read eligible Lists and the minimum Item fields needed for counts, using complete paginated reads and client aggregation. Load complete Item content only for the opened List.

Do not add SQL views/RPCs solely for counts, denormalized counters, or cached completion state in v1. If real List volume makes full overview aggregation expensive, measure before changing this design.

## 14. Navigation and UI hierarchy

    功能中心 → 清单总览 → 清单详情

Keep the existing React memory navigation. Add only the stable navigation target needed to restore a List detail and revalidate Space membership, module eligibility, and List access on restore. Do not add a Router, URL/deep-link system, or navigation redesign.

Overview:

- independent listFilter, default 全部空间;
- explicit + creation action with Space target;
- 进行中 and default-collapsed 已完成 groups;
- deterministic created_at descending order;
- name, eligible source Space label when aggregating, and item-derived progress.

Detail:

- List name with lightweight rename and a two-step delete confirmation that identifies the List and its Space both times;
- ungrouped active Items first, with quick-add and a collapsed completed fold;
- optional Sections in canonical order, each with collapse, inline rename, quick-add, active Items, and its own collapsed completed fold;
- inline add-section control;
- accessible item drag handles for ungrouped or same-Section reorder;
- no author labels.

Lists do not automatically add a Home summary or appear in Calendar.

## 15. Notifications and product distinction

Shared Lists v1 has no Push notification, reminder, notification preference, or background notification. Changes synchronize through Realtime only while the app is open.

Task remains assigned work with optional due date and existing completion semantics. List is a jointly maintained set of short items. Do not reuse the tasks table to represent Lists.

## 16. Explicit non-goals

Do not add:

- Push, reminders, assignee, due date, priority, quantity field, notes, comments, attachments;
- author labels, approval workflow, Suggested Edit, or activity log;
- archive, search, templates, duplicate/copy, favorite/pin, or export;
- AI, voice, images/photos, or other media;
- Home summary or Calendar projection/Event generation;
- recursive nesting or more than List → Section → Item;
- cross-List or cross-Space drag;
- three-person Space implementation;
- Router/navigation rewrite or visual-system rewrite.

## 18. Verification and acceptance strategy

The Design Freeze itself ran no tests or build. Slice 1 local DB and Production rollout/postflight results are recorded in [TESTING](./TESTING.md); no Lists frontend build or authenticated acceptance is claimed.

### Database tests

- Personal/Shared membership, Lists module enabled/disabled, disabled historical reads, and disabled write rejection;
- RLS isolation for non-members, creator-independent shared edits, immutable identity, and parent/Section consistency;
- Space/List cascades and member leave/remove/ownership-transfer retention;
- Section delete-preserve ordering and Section delete-with-items atomicity;
- List delete cascade, item delete, and operation rejection after eligibility changes;
- concurrent append/reorder, stale reorder rejection, completed/reopened sort preservation, and Section-delete versus Item-create serialization;
- Realtime publication and exact filtered UPDATE/DELETE behavior under RLS and REPLICA IDENTITY FULL.

### Node/frontend tests

- List completion and progress derivation, including empty List and empty Section cases;
- overview created_at ordering and deterministic tie behavior;
- independent listFilter and eligible Space normalization;
- completed folds preserving canonical order;
- quick-add trimming, Enter handling, input clearing, and focus retention;
- delete-choice request shape and stale mutation reconciliation;
- Realtime refresh deduplication, active overview/detail subscription boundaries, eligibility-loss cleanup, and navigation restore validation.

### Dual-account / manual acceptance

- Personal Space create/edit/delete and module disable/re-enable behavior;
- Shared Space two-account CRUD, editing by either member, completion/reopen, item and Section reorder, deletion semantics, and live updates without refresh;
- filtered DELETE delivery while the other account is subscribed;
- stale membership/module state clears on focus/reconnect or rejected mutation;
- 320px and supported mobile/PWA quick-add keyboard behavior, target sizes, folds, drag scrolling, drag cancellation, and keyboard fallback.

Codex owns automated verification and environment alignment. Users perform real OTP, two-account, authenticated browser, and device/PWA acceptance. Codex does not drive those logged-in sessions.
