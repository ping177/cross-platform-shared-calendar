## Objective and invariants

Make the four destinations `首页 / 日历 / 空间 / 我的` useful with the currently implemented Event and Task modules. Every Event and Task retains exactly one canonical `space_id`: **ownership ≠ view**. Aggregation is a read-only view of membership-visible canonical objects, never a second write model. A `personal` Event inside a Shared Space remains visible to that Space's members; it is not a private Personal Space Event.

Preserve existing Event scope/owner permissions, Reminder and recurrence/exception behavior, Task identity/assignment/status permissions, the Shared Space two-member cap, and the rule that disabling Tasks hides its UI without deleting history while the database blocks mutations.

## Navigation and state contract

| Destination | v0.1.11 responsibility |
| --- | --- |
| 首页 | Bounded summary of Event and attention-needed Task data from all membership-visible Spaces, plus global `+`. |
| 日历 | Event time aggregation with `全部空间 / 单个 Space` filter and explicit Space attribution. |
| 空间 | Personal and Shared Space list, current Space marker, existing Hub, Shared create/join, Calendar core and enabled modules. |
| 我的 | Existing display name, logout, and this-device notification settings; no generic device list or settings framework. |

`selectedSpaceId` means the concrete current Space for Hub, module settings, Space-local flows and creation context. It is not the Calendar aggregation filter. Calendar uses `calendarFilter = 'all' | { spaceId: string }`; derive `visibleSpaceIds` from membership-validated `spaces[]` and that filter, never maintain it as independent mutable ownership state. Home always uses all membership-visible Spaces, independent of `selectedSpaceId`. A Space change cannot silently change Calendar filter; an explicit “view this Space's calendar” action may set it. Invalid filter IDs reset safely to `all` after membership refresh.

Keep the existing per-user validated `selectedSpaceId` device storage. Tab, Calendar filter and create target are React state; do not persist them to database or cross-session storage. Account changes clear all aggregate results, filters and open Sheets. Refresh/PWA reopen may start at Calendar before Slice 3 makes Home visible, then at Home with the all-Space filter after Slice 3; a validated current Space can still be restored. Tabs, filter, current Space and create target must not mutate each other implicitly.

## Calendar aggregation and canonical navigation

- Query only membership-visible `space_id` values. Read complete Event source data with explicit pagination/completeness handling; read exceptions in bounded batches by actual Event IDs. Existing Today/Week/Month recurrence projection, only-this/current-and-future exceptions and Reminder semantics stay authoritative. Do not silently render partial data as a complete calendar.
- Show a readable Space label for aggregate Event items and use members from the Event's own `space_id` for owner/audience labels. Retain canonical `event.id`, `space_id`, `scope` and `owner_user_id` in the view model. Clicking an Event opens the existing Event detail/edit Sheet with that Event's Space and members; no aggregate editor or ownership migration.
- The filter offers only all Spaces or exactly one Personal/Shared Space. No subset multiselect, external sources or saved cross-session filter. Fast filter/membership/account changes invalidate previous reads, clear obsolete results, and tear down obsolete subscriptions before accepting new results.
- Realtime remains bounded and uses the existing per-`space_id` Event channel strategy. Subscribe only while the active view needs those Spaces; unsubscribe on view exit, filter, membership or account change. Do not leave aggregate and Space-local views subscribed to the same source indefinitely. Reconnect/re-entry causes an authoritative read. The existing occurrence RPCs update their source Event, triggering Event refresh; no exception publication is added.
- Personal Space plus an existing Shared Space is sufficient for real aggregation acceptance. Shared ↔ Shared is additional coverage only if the account already has two Shared Spaces; otherwise record `N/A`. Never create a Production Shared Space solely for testing.

## Home and Task aggregation

Home is a small all-Spaces summary, not a dashboard framework. Show current/upcoming Event occurrences over a bounded near-term window and open, attention-needed Tasks (assigned to this user or shared/unassigned; overdue, today, near-term due, and a small undated remainder). Sort deterministically by effective date/time and stable ID ties, then apply small display limits chosen in the Slice 3 implementation plan. Each item has a Space label; no large per-Space grouping or preference/config system. Completed Tasks and Tasks assigned only to another member are absent from the attention-needed summary.

Read Tasks only for membership-valid Spaces whose `tasks` module state is authoritatively `enabled=true`. Disabled, absent, loading, error and unknown state is not permission to display or mutate aggregate Tasks; present a comprehensible retry/error state. Leaving Home tears down Home-only Event/Task subscriptions. Module state is not in Realtime: refresh on Home re-entry/focus/reconnect and after local toggles; a remote toggle may remain visually stale in an already-open page until refresh, while database policy immediately blocks forbidden writes. Do not add `space_modules` to Realtime in this version.

Home Task clicks retain canonical `task.id`, `space_id`, assignment and status and open the existing Task detail/edit semantics for that Space. If the module has become disabled, close/disable the aggregate edit path and respect the backend restriction. `due_on` Task-to-Calendar projection is deferred; Task remains Task and never writes into `events`.

## Global create and wrong-Space protection

The global `+` offers only 日程 and 任务. Create mode reuses `EventSheet`/`TaskSheet`, with an independent `targetSpaceId`, a visible `保存到：<Space>` target selector, a primary action naming the Space, and a second explicit target confirmation before mutation. Editing an existing Event or Task keeps its original Space fixed.

| Context | Default target |
| --- | --- |
| Concrete Space/Hub | That membership-valid Space. |
| Calendar filtered to exactly one Space | That Space. |
| Home, all-Space Calendar, or ambiguous context | Personal Space. |

Never silently fall back to Shared Space. If Personal Space initialization failed, global Event/Task creation has no implicit target; a user who continues must explicitly choose a membership-valid Space. On every target change, revalidate/reset Space-specific audience or assignee and cancel an old confirmation. Before the actual insert, validate current account, target membership and canonical Space; for Tasks also re-read module state and require `enabled=true`. Disabled/loading/error/unknown modules are ineligible Task targets.

When the default Personal Space has Tasks disabled, keep the Personal default visible but require the user to explicitly choose an enabled target; do not switch to Shared automatically. If there is no Tasks-enabled Space, explain why Task creation is unavailable **before opening a Task Sheet**. Do not auto-enable or change any module. A submitted Sheet cannot use a stale `selectedSpaceId` or another account's remembered target.

Expected implementation is frontend-only: current member-scoped Event/Task/exception RLS and `space_id` queries support the read model. No schema, SQL patch, aggregate RPC/table/service, duplicated persistence, state framework or new production dependency is planned. This is a repository-level design conclusion; before any authenticated acceptance, recheck the actual frontend backend target, required Production schema/RPC/Realtime capabilities and version compatibility under the project's authenticated integration readiness gate.

No planned first-run persistent write makes the currently served v0.1.10 frontend incompatible. Subject to that gate and reviewed implementation, user-run local frontend + Production backend authenticated acceptance can precede deployment; do not mechanically reuse the v0.1.10 deploy-before-test exception. Codex owns automated checks and environment alignment. The user owns OTP/Magic Link, A/B browser, iPhone/Android and PWA authenticated acceptance. Commit, push and deploy require separate explicit authorization.
